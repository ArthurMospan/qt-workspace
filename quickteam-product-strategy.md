## 1. Must-have

Це функції, які присутні у кожному зрілому таск-менеджері. Без них QuickTeam не може замінити Trello, Jira або Asana для більшості команд.

---

### 1.1 Система сповіщень

**Що відсутнє:** Email, push, in-app — жодного каналу немає. Користувач не дізнається, що йому призначили задачу, залишили коментар або настає дедлайн.

**Чому критично:** Без сповіщень асинхронна командна робота неможлива. Це перша причина, через яку команди відмовляться від продукту.

**Як реалізувати:**
- In-app bell: real-time через Firestore listener або WebSocket
- Email: Resend або Postmark, 5 базових тригерів (призначення, @mention, дедлайн за 24г, зміна статусу, коментар)
- Web push: Firebase Cloud Messaging
- Налаштування per-user: які події → яка доставка

---

### 1.2 Календарний вигляд (Calendar View)

**Що відсутнє:** Немає можливості побачити дедлайни на часовій осі. Kanban показує стан задач, але не їх розподіл у часі.

**Чому критично:** PM-и планують спринти відносно реального календаря. Без Calendar view неможливо знайти перевантажені тижні або побачити конфлікти дедлайнів.

**Як реалізувати:**
- Додати Calendar як третій режим перегляду (Board / Backlog / Calendar)
- Відображати задачі за полем `due_date`
- Drag-to-reschedule прямо в календарі
- Monthly / Weekly перемикач
- iCal-експорт для синхронізації з Google Calendar / Apple Calendar
- Бібліотека: `FullCalendar` або `react-big-calendar`

---

### 1.3 Шаблони задач і проектів

**Що відсутнє:** Кожна задача і кожен проект створюються з нуля. Немає збережених структур.

**Чому критично:** Команди повторюють одні й ті ж структури щотижня: bug report, feature request, onboarding checklist, sprint kickoff. Без шаблонів — втрачається послідовність і витрачається час.

**Як реалізувати:**
- Бібліотека шаблонів задач: назва, тип, поля, чекліст підзадач, опис
- Шаблони проектів: набір колонок + стартові задачі
- Кнопка «Зберегти як шаблон» на будь-якій задачі або проекті
- Базовий набір з 5–7 готових шаблонів одразу після реєстрації

---

### 1.4 Recurring tasks (повторювані задачі)

**Що відсутнє:** Немає можливості автоматично створювати задачі за розкладом.

**Чому критично:** Стендапи, weekly reports, місячні ревью — повторюються постійно. Навіть Todoist на безкоштовному плані це вміє. Без цього QuickTeam програє мінімальним конкурентам.

**Як реалізувати:**
- Поле `recurrence` у задачі: щодня / щотижня / щомісяця / кастомний інтервал
- Firebase Cloud Function або cron-задача, що автоматично створює наступний екземпляр після закриття поточного
- Recurring-іконка на картці задачі
- Можливість редагувати «всі» або «лише цю» при зміні

---

### 1.5 Реальні залежності між задачами

**Що відсутнє:** Issue Links є, але декоративні — блокована задача ніяк не виділяється, дедлайни не каскадуються.

**Чому критично:** Якщо задача A блокує B, і B нічим не позначена — блокери стають марними. Команди будуть ігнорувати цю функцію.

**Як реалізувати:**
- Lock-іконка і warning-колір на заблокованих задачах у Kanban і My Tasks
- Computed-поле `isBlocked`: true, якщо є хоч один незакритий blocking-зв'язок
- Tooltip: «Заблоковано задачею #ID»
- Опціонально: Timeline / Gantt view зі стрілками залежностей (наступний етап)

---

### 1.6 Вкладення файлів до задач

**Що відсутнє:** Неможливо прикріпити файл, скріншот, дизайн або документ до задачі.

**Чому критично:** У реальному workflow дизайнери прикріплюють Figma-посилання і скрини, розробники — логи, менеджери — ТЗ. Без цього задачі залишаються контекстно бідними.

**Як реалізувати:**
- Drag-and-drop або кнопка «Прикріпити» в TaskDetailPanel
- Зберігання: Firebase Storage або AWS S3
- Preview для зображень (thumbnail)
- Ліміти для Free-плану: 5 MB на файл, 100 MB на проект
- Підтримка: PNG, JPG, PDF, ZIP, MP4 (з лімітом)

---

### 1.7 Activity log / Audit trail

**Що відсутнє:** Немає журналу активності ні на рівні задачі, ні на рівні проекту. Якщо хтось змінив пріоритет або видалив коментар — слідів немає.

**Чому критично:** Для командної роботи потрібна прозорість. «Хто і коли змінив статус» — базова вимога будь-якого корпоративного інструменту.

**Як реалізувати:**
- Вкладка «Активність» у TaskDetailPanel: хронологічний список подій
- Сторінка «Активність проекту» на рівні workspace
- Зберігати події в окрему Firestore-колекцію з TTL: 90 днів (Free), без ліміту (Pro)
- Типи подій: зміна статусу, призначення, дедлайн, додавання/видалення коментаря, прикріплення файлу

---

### 1.8 Глобальний пошук (Cmd+K)

**Що відсутнє:** Щоб знайти задачу — потрібно знати, в якому проекті вона є, і вручну гортати. Command palette відсутній.

**Чому критично:** Cmd+K — базовий UX-стандарт для workspace-інструментів 2024+. Його відсутність одразу знижує сприйняття рівня продукту.

**Як реалізувати:**
- Command palette через бібліотеку `cmdk` (від Vercel, React-native)
- Пошук по задачах, проектах, учасниках, коментарях у real-time
- Fuzzy search (нечіткий пошук)
- Фільтрація результатів по типу
- Клавіатурна навігація стрілками + Enter для переходу

## 2. Зростання

Функції, що перетворюють QuickTeam з ізольованого інструменту на платформу та відкривають нові сегменти клієнтів.

---

### 2.1 Дашборд аналітики та звітність

**Чого не вистачає:** Немає жодної агрегованої картини: скільки задач закрито, хто перевантажений, які спринти зриваються.

**Що додати:**
- Burndown chart активного спринту
- Velocity по спринтах (trend-графік)
- Розподіл відкритих задач по учасниках (bar chart)
- % виконання в строк (on-time delivery)
- Time tracking summary по проекту і по учаснику
- Щотижневий email-звіт (digest)
- Експорт у CSV та PDF

---

### 2.2 Інтеграції та вебхуки

**Чого не вистачає:** QuickTeam існує у вакуумі. Команди хочуть, щоб новий інструмент вписався в їх поточний стек, а не замінив його.

**Пріоритет інтеграцій:**
1. **Slack** — сповіщення в канали при зміні статусу, @mention, новій задачі
2. **GitHub / GitLab** — прив'язка PR до задачі, автозакриття задачі при merge
3. **Google Calendar** — двостороння синхронізація дедлайнів
4. **Zapier / Make** — incoming webhook endpoint (найшвидший шлях до екосистеми)
5. **Import** з Jira, Trello, Asana (CSV або API)

---

### 2.3 Гостьовий доступ та Client Portal

**Чого не вистачає:** Client Portal задекларований як ключова фіча, але порталу немає — ні UI, ні навігаційного пункту.

**Що реалізувати:**
- Invite by email → guest-роль з доступом лише до дозволених проектів
- Кастомний view без sidebar QuickTeam (white-label опціонально)
- Права клієнта: переглядати задачі, залишати коментарі, схвалювати deliverables (approval-кнопка)
- Шарувальне посилання без необхідності реєстрації (token-based)
- Окремий лог активності клієнта

---

### 2.4 Мобільний додаток або PWA

**Чого не вистачає:** Немає мобільного доступу — лише десктоп.

**Мінімальний шлях (PWA):**
- Service Worker + IndexedDB для offline-режиму
- Фокус на: My Tasks, зміна статусу, додавання коментарів, перегляд сповіщень
- Web Push API для нативних push-сповіщень
- Installable на iOS (Safari) і Android (Chrome)
- Повноцінний React Native — наступний етап після Product-Market Fit

---

### 2.5 AI-асистент для задач

**Чого не вистачає:** Жодної автоматизації або розумних підказок. Конкуренти (Linear, Notion, Asana) вже мають AI-функції.

**Реалістичні фічі зараз (через Anthropic API):**
- «Розбити задачу на підзадачі» — один клік, генерація за назвою + описом
- «Summarize sprint» — генерація звіту завершеного спринту
- Автопропозиція assignee на основі минулих задач аналогічного типу
- Detect duplicate — попередження при створенні схожої задачі
- Пріоритизація беклогу — AI-ранжування за impact/effort

## 3. Диференціація

Функції, що дозволяють QuickTeam виграти у конкурентів у конкретних нішах і виправдати вищу ціну.

---

### 3.1 Розширений Time Tracking з білінгом клієнту

**Чому диференціює:** Таймер і логи вже є. Наступний крок — виставляти рахунок клієнту за витрачений час. Для агенцій і фрілансерів це killer feature.

**Що додати:**
- Billable / non-billable toggle на кожному записі часу
- Hourly rate per project або per member
- Invoice generator: проект + діапазон дат → PDF-рахунок з деталізацією по задачах
- Stripe-інтеграція для онлайн-оплати
- Звіт по billable hours за місяць

---

### 3.2 Intake Forms (форми збору запитів)

**Чому диференціює:** Клієнт хоче подати баг або запит, але не має акаунту. Зараз немає варіанту — він пише в месенджер, хтось вручну створює задачу.

**Що додати:**
- Конструктор форм: назва, тип, пріоритет, опис, вкладення
- Публічне посилання без авторизації
- Сабміт форми → автоматично нова задача в обраному проекті з обраним assignee
- Email-підтвердження відправнику
- Ніякого кодингу для налаштування — pure no-code

---

### 3.3 Goals / OKR-трекер

**Чому диференціює:** Задачі є, але немає відповіді на питання «навіщо?». OKR-трекер піднімає QuickTeam з операційного рівня на стратегічний.

**MVP-підхід:**
- Сторінка Goals: назва, метрика (число або %), поточне значення, target
- Прив'язка проектів до Goal
- Автоматичний прогрес на основі закритих задач
- Weekly check-in reminder
- Rollup прогресу з підзадач
- Team goals vs Company goals (ієрархія)

---

### 3.4 Automation Rules (якщо-то правила)

**Чому диференціює:** Linear і Jira мають automation. QuickTeam може реалізувати спрощений варіант без коду, що заощадить командам годинну роботу щотижня.

**Початкові 10 правил:**
1. Призначено задачу → встановити статус «In Progress»
2. Пріоритет «Critical» → призначити Team Lead
3. Задача прострочена → сповістити виконавця
4. Спринт завершений → перемістити незакриті задачі в Backlog
5. Label «bug» → встановити пріоритет «High»
6. PR змерджено (GitHub) → встановити статус «Done»
7. Нова задача в проекті → додати стандартний чекліст
8. Задача переміщена в «Done» → сповістити reporter
9. Коментар від клієнта → сповістити PM
10. Дедлайн через 3 дні → показати нагадування

**UI:** Zapier-подібний конструктор «тригер → дія» без коду.

---

### 3.5 Table / Spreadsheet View

**Чому диференціює:** Частина команд (PM-и, аналітики) мислять таблицями, не картками. Notion і Linear мають, QuickTeam — ні.

**Що додати:**
- Table як четвертий view (Board / Backlog / Calendar / Table)
- Кожна задача — рядок, поля — колонки (назва, assignee, status, priority, due date, estimate, labels)
- Inline edit будь-якого поля
- Bulk select + bulk edit (зміна статусу для 10 задач одним кліком)
- Frozen перша колонка при горизонтальному скролі
- CSV export

---

### 3.6 Workload View (завантаженість команди)

**Чому диференціює:** Менеджер не може побачити, що в одного учасника 12 задач, а в іншого — 2. Workload view вирішує це до того, як спринт зривається.

**Що додати:**
- Тижнева сітка: кожен учасник — рядок, тижні — колонки, задачі — блоки
- Heat map перевантаженості (зелений → жовтий → червоний)
- Capacity в годинах (estimate) vs реальне навантаження
- Drag задачі між учасниками прямо з Workload view
- «Overloaded» warning badge при перевищенні capacity
- Фільтр по проекту

## Висновок

QuickTeam має міцну технічну основу і гарний UI-напрямок. Зараз продукт знаходиться на рівні MVP+, але ще не є повноцінним таск-менеджером через відсутність базових функцій (сповіщення, пошук, файли, calendar).

Найшвидший шлях до product-market fit:

1. **Q3 2026** — закрити must-have прогалини: search, notifications, files, activity log. Це займе ~5–6 тижнів і одразу виведе продукт на конкурентний рівень для малих команд.
2. **Q4 2026** — calendar view і Client Portal відкривають агентський сегмент, де QuickTeam може виграти через billable time tracking (якого немає у Linear або Notion).
3. **Q1–Q2 2027** — automation, workload, AI — це перехід від «інструменту» до «платформи», що виправдовує вищий price point.

Унікальна ніша QuickTeam — **агенції і продуктові команди, що працюють з клієнтами**. Саме тут billable tracking + Client Portal + intake forms + project templates створюють combination, якої немає у жодного прямого конкурента.

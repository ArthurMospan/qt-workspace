# QuickTeam Workspace — задачі для виконання

Цей файл — виконавчий план на основі ревю проєкту (2026-07-01). Признач для IDE-агента (Claude Code, Cursor тощо), що працює всередині репозиторію `qt-workspace`.

## Інструкція для агента — прочитай перед стартом

1. Виконуй роботу **хвилями**, у порядку нижче. Не перескакуй наперед і не змішуй задачі з різних хвиль в одному діффі.
2. Після завершення хвилі — **зупинись**, коротко опиши що зробив і що варто перевірити вручну, і чекай підтвердження власника проєкту, перш ніж братись за наступну хвилю.
3. **Не комить і не пуш самостійно.** Залиш зміни в робочій копії для перегляду.
4. Файли й номери рядків нижче орієнтовні — код міг трохи змінитися відтоді, як писалось ревю. Перед правкою звір із поточним станом файлу.
5. Розділ **"Виключено — не чіпати"** в самому кінці — це задачі, які свідомо не входять у жодну хвилю. Не виконуй їх, навіть якщо здається, що це логічно й просто. Вони чекають на рішення власника продукту або дизайнера.
6. Якщо для якоїсь задачі не знаходиш вказаний файл/рядок або код виглядає інакше — не вгадуй і не імпровізуй, опиши розбіжність і став питання.

## Хвиля 5 — Firestore rules (окремо, з ручною перевіркою)

Не перша хвиля, але обов'язкова **до того, як логін у застосунок отримає хтось другий** (тімейт, тестувальник, клієнт) — зараз доступ має лише власник, тому це не терміново, але й відкладати надовго не можна.

- **T1.** Переписати `firestore.rules` (корінь `qt-workspace`). Зараз: `match /{document=**} { allow read, write: if request.auth != null; }` — будь-який залогінений користувач читає/пише/видаляє будь-який документ будь-якої організації. Замінити на структурне правило, що перевіряє належність до організації через колекцію `orgMemberships` (ключ документа `{orgId}_{uid}`), а не по кожному полю окремо — так майбутні зміни схеми не вимагатимуть постійного переписування правил. Напрямок:

  ```
  function isOrgMember(orgId) {
    return request.auth != null &&
      exists(/databases/$(database)/documents/orgMemberships/$(orgId + '_' + request.auth.uid));
  }
  match /projects/{projectId} {
    allow read, update, delete: if isOrgMember(resource.data.organizationId);
    allow create: if isOrgMember(request.resource.data.organizationId);
  }
  // той самий патерн повторити для: tasks, issues, sprints, timeLogs, issueLinks, invitations, organizations
  ```

  Це початковий напрямок, не фінальні правила — звірити з кожною колекцією окремо (особливо `users` і `presence`, які не завжди прив'язані до однієї організації).

**Обов'язково перед деплоєм:** протестувати через Firebase emulator (або вручну кількома тестовими акаунтами: owner, admin, member, client — і мінімум двома різними організаціями), що (а) легітимний доступ у межах своєї організації й далі працює, (б) доступ до чужої організації тепер заблоковано. Не деплоїти без цієї перевірки.

## Крок 1. Згенеруй два секрети

У будь-якому терміналі:

```bash
# 1) Спільний секрет клієнта (той самий рядок піде в ОБИДВА проєкти)
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

# 2) Ключ шифрування токенів (лише для workspace)
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Збережи обидва десь у себе (менеджер паролів).

> **Чому нові, а не ті, що вже в `.env.local`?**
> Локальні я згенерував у чаті — отже вони засвітились у транскрипті. Для прода
> це те саме, що ключ, вставлений у чат (уже проходили це у Фазі 0: довелось
> відкликати). Локальні лишаються локальними, прод отримує свіжі.

## Крок 2. Env-змінні у Vercel проєкт `qt`

Vercel → проєкт **qt** → Settings → Environment Variables.
Обери **Production** і **Preview** для обох.

| Name | Value |
|---|---|
| `QTPLUS_WORKSPACE_CLIENT_SECRET` | ← секрет №1 з кроку 1 |
| `QTPLUS_WORKSPACE_REDIRECT_URIS` | `https://qt-workspace.vercel.app/api/integrations/qtplus/callback` |

> `QTPLUS_WORKSPACE_REDIRECT_URIS` — білий список адрес повернення, точний збіг.
> Якщо захочеш ще й локально проти прод-QT+, додай через кому, без пробілів:
> `https://qt-workspace.vercel.app/api/integrations/qtplus/callback,http://localhost:3000/api/integrations/qtplus/callback`

## Крок 3. Env-змінні у Vercel проєкт `qt-workspace`

Vercel → проєкт **qt-workspace** → Settings → Environment Variables.
**Production** і **Preview**.

| Name | Value |
|---|---|
| `NEXT_PUBLIC_QTPLUS_URL` | `https://qt-green.vercel.app` |
| `QTPLUS_CLIENT_SECRET` | ← **той самий** секрет №1, що і в `qt` |
| `QTPLUS_TOKEN_KEY` | ← ключ №2 з кроку 1 (base64) |

> ⚠️ `QTPLUS_CLIENT_SECRET` мусить збігатися з `QTPLUS_WORKSPACE_CLIENT_SECRET`
> символ у символ. Не збігнеться → обмін коду впаде з 401.
>
> ⚠️ `QTPLUS_TOKEN_KEY` має бути **до** першого підключення. Зміниш пізніше —
> усі збережені гранти стануть нечитабельними, всім доведеться перепідключатись
> (шляху перешифрування у Phase 1 немає, свідомо).

## Крок 4. Redeploy workspace ← найлегше пропустити

`NEXT_PUBLIC_QTPLUS_URL` **вшивається на етапі білду**, а не читається в рантаймі.
Просто додати змінну — недостатньо, секція не з'явиться.

Vercel → проєкт **qt-workspace** → Deployments → останній → **⋯ → Redeploy**.

`qt` теж передеплой (його змінні рантаймні, але так надійніше й швидше, ніж
з'ясовувати чому 500).

## Крок 5. Увімкни інтеграцію для організації

У workspace: **Налаштування → Інтеграції → QuickTeam+ → тумблер увімкнено**.

Це вже наявний прапорець `qtPortalEnabled` — новий я не додавав. Без нього
персональна секція покаже «Інтеграцію вимкнено для цієї організації».

## Крок 6. Перевір флоу в браузері (це те, що я зробити не міг)

1. **Налаштування → QuickTeam+** (розділ «Особисте», не «Інтеграції»).
   Якщо секції немає → крок 4 не спрацював.
2. **Підключити** → має відкритись екран згоди на `qt-green.vercel.app`.
   Якщо ти не залогінений у QT+ — спершу логін, потім згода.
3. **Дозволити** → повертає в налаштування, тост «QuickTeam+ підключено»,
   у картці видно email твого QT+ акаунта.
4. **Відключити** → тост «QuickTeam+ відключено», картка знову пропонує підключити.

### Що перевірити у Firestore (варте 2 хвилин)

- **`quickteam-me`** → `users/{твій uid}/private/qtplus`
  → поле `refreshTokenBox` = `{v, iv, tag, data}`, нечитабельний шифротекст.
  **Ніде не має бути токена відкритим текстом.**
- **`quickteam-portal-prod`** → `oauthGrants`
  → один новий документ. **ID документа — це хеш, не сам токен.**
  Після «Відключити» в ньому має з'явитись `revokedAt`.

## Якщо щось пішло не так

| Симптом | Причина |
|---|---|
| Секції QuickTeam+ немає | `NEXT_PUBLIC_QTPLUS_URL` не задано **або** не зробив redeploy (крок 4) |
| «Інтеграцію вимкнено для організації» | тумблер у Інтеграції вимкнений (крок 5) |
| «Інтеграцію QuickTeam+ не налаштовано на сервері» | немає `QTPLUS_CLIENT_SECRET` або `NEXT_PUBLIC_QTPLUS_URL` у workspace |
| Повертає з `qtplusError=exchange` | секрети в двох проєктах не збігаються, **або** `redirect_uri` не в білому списку `qt` |
| Повертає з `qtplusError=state` | посилання протухло / відкрите в іншому браузері. Просто почни заново — так і має бути |
| Екран згоди каже «Некоректний запит» | `client_id` не дійшов — перевір `NEXT_PUBLIC_QTPLUS_URL` |
| На `qt` 500 у `/api/oauth/*` | не задані env-змінні кроку 2 |

Логи: Vercel → проєкт → Deployments → Runtime Logs. Усі помилки логуються
з префіксами `[qtplus]` та `[api/oauth/...]`.

## Що НЕ входило в Phase 1 (щоб не шукав)

Phase 1 — це **тільки підключення акаунта**. Після нього ще нічого не видно в
проєктах: ні чату QT+, ні етапів, ні матеріалів. Це Фази 2–4:

- **Фаза 2** — живі дані: обмін гранта на scoped Firebase custom token.
  `lookupGrant()` для цього вже готовий і протестований.
- **Фаза 3** — лінкування конкретного проєкту workspace ↔ проєкт QT+ + пікер.
- **Фаза 4** — UI: таб «QuickTeam+», етапи, матеріали, чат.

## Відкриті борги (не блокують Phase 1)

- `users.read` / `users.update` у **qt** відкриті будь-якому залогіненому —
  будь-хто читає будь-який профіль. Потрібна перевірка «є спільний проєкт»,
  однорядковим фіксом не закривається.
- `notifications.create` у **qt** відкритий — можна підробити сповіщення будь-кому.
  Має лишатись відкритим, поки живий клієнтський `notifyTeam`.
- Ролі в **qt** застосовуються **лише** при створенні інвайта. Viewer досі може
  перейменувати проєкт, видаляти етапи/матеріали, редагувати чужі повідомлення.
- `getAdminApp()` у **workspace** має обидва баги, які вже виправлені в qt:
  підхоплює чужий default-app і тихо стартує **без credential**, якщо
  `FIREBASE_CLIENT_EMAIL`/`FIREBASE_PRIVATE_KEY` не задані.
- `npm run lint` у **qt** — 74 проблеми, усі давні (не з Phase 1, перевірено).
